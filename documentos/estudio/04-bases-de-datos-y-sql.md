# 04 — Bases de datos y SQL

## 1. Qué es una base de datos relacional

Una **base de datos** es un programa que guarda información de forma ordenada, segura y
permanente (sobrevive a que se apague la computadora), y permite consultarla rápido.

Una base **relacional** guarda los datos en **tablas**, como planillas de Excel:

**Tabla `medicamento`**

| id | codigo | nombre | presentacion | stock_minimo | activo |
|---|---|---|---|---|---|
| 1 | AMOX-500 | Amoxicilina | comprimidos 500 mg | 200 | true |
| 2 | CEFT-1G | Ceftriaxona | frasco ampolla 1 g | 80 | true |
| 5 | PARA-500 | Paracetamol | comprimidos 500 mg | 300 | true |

- Cada **fila** (registro) es un medicamento.
- Cada **columna** (campo, atributo) es un dato, con un **tipo** fijo.

Usamos **PostgreSQL 16**: libre, gratuita, muy robusta.

## 2. Claves

### Clave primaria (PK)

Columna que **identifica de forma única** cada fila. Como el DNI de una persona. En todas las
tablas del proyecto es `id`, un número que la base asigna sola (1, 2, 3…).

```sql
id bigint generated by default as identity primary key
```

### Clave foránea (FK)

Columna que **apunta** a la clave primaria de otra tabla. Así se relacionan las tablas.

**Tabla `lote`**

| id | medicamento_id | proveedor_id | numero_lote | fecha_vencimiento | cantidad_actual |
|---|---|---|---|---|---|
| 10 | **5** | 2 | L2301 | 2026-12-01 | 100 |
| 14 | **5** | 1 | L2340 | 2027-03-15 | 410 |

`medicamento_id = 5` quiere decir "este lote es del medicamento 5" (Paracetamol). La base **no
deja** cargar un `medicamento_id` que no exista: eso es **integridad referencial**.

```sql
medicamento_id bigint not null references medicamento (id)
```

> **Ojo:** el lote **no repite** el nombre "Paracetamol". Guarda solo el número 5. Si mañana se
> corrige el nombre del medicamento, se corrige en un solo lugar. Eso es **normalización**.

### Clave sustituta vs. natural

- **Natural**: un dato del negocio que ya es único (el CUIT, el código del medicamento).
- **Sustituta**: un número inventado (`id`) sin significado.

El proyecto usa **sustitutas** como PK, y protege las naturales con `UNIQUE`. Así, si un código se
cargó mal, se corrige sin romper todas las relaciones.

## 3. Relaciones

| Tipo | Ejemplo | Cómo se arma |
|---|---|---|
| **Uno a muchos (1:N)** | Un medicamento tiene muchos lotes. | FK en el lado "muchos": `lote.medicamento_id`. |
| **Muchos a muchos (N:M)** | Una transferencia usa muchos lotes y un lote se reparte en muchas transferencias. | **Tabla intermedia**: `detalle_transferencia` con dos FK (`transferencia_id`, `lote_id`) y la cantidad. |
| **Uno a uno (1:1)** | No hay en el proyecto. | FK única. |

## 4. Restricciones (reglas que la base hace cumplir)

| Restricción | Qué hace | Ejemplo del proyecto |
|---|---|---|
| `NOT NULL` | El campo es obligatorio. | `nombre varchar(120) not null` |
| `UNIQUE` | No se puede repetir. | `constraint uq_medicamento_codigo unique (codigo)` |
| `CHECK` | Condición que tiene que cumplirse. | `check (cantidad_actual >= 0 and cantidad_actual <= cantidad_inicial)` |
| `PRIMARY KEY` | Único y no nulo. | `id` |
| `REFERENCES` (FK) | Tiene que existir en la otra tabla. | `references medicamento (id)` |
| `DEFAULT` | Valor si no se manda. | `activo boolean not null default true` |

> **Para la defensa:** "El `CHECK` de `cantidad_actual >= 0` es la **última barrera**: aunque el
> código Java tuviera un error, la base rechaza un stock negativo."

## 5. SQL: el idioma de la base

**SQL** (*Structured Query Language*) es el lenguaje para hablarle a la base.

### Crear tablas (DDL)

```sql
create table area (
    id      bigint generated by default as identity primary key,
    nombre  varchar(80) not null,
    activo  boolean     not null default true
);
```

### Insertar, leer, modificar (DML)

```sql
-- Insertar
insert into area (nombre, activo) values ('Guardia', true);

-- Leer: todas las áreas activas, ordenadas por nombre
select id, nombre from area where activo = true order by nombre;

-- Modificar: desactivar el área 3 (baja lógica)
update area set activo = false where id = 3;

-- Borrar (en el proyecto NO se usa)
delete from area where id = 3;
```

### Juntar tablas (JOIN)

Para mostrar el lote con el nombre del medicamento, se **juntan** las dos tablas por la FK:

```sql
select l.numero_lote, m.nombre, l.fecha_vencimiento, l.cantidad_actual
from lote l
join medicamento m on m.id = l.medicamento_id
where l.cantidad_actual > 0;
```

| numero_lote | nombre | fecha_vencimiento | cantidad_actual |
|---|---|---|---|
| L2301 | Paracetamol | 2026-12-01 | 100 |
| L2340 | Paracetamol | 2027-03-15 | 410 |

- `join` (o `inner join`): solo filas que tienen pareja en las dos tablas.
- `left join`: todas las filas de la izquierda, aunque no tengan pareja (con `null` en la derecha).
  Se usa para listar **todos** los medicamentos, incluso los que no tienen lotes.

### Agrupar y sumar

```sql
-- Stock total por medicamento (solo lotes con stock y no vencidos)
select medicamento_id, sum(cantidad_actual) as stock, min(fecha_vencimiento) as proximo
from lote
where cantidad_actual > 0 and fecha_vencimiento >= '2026-11-12'
group by medicamento_id;
```

`sum`, `min`, `max`, `count`, `avg` son **funciones de agregación**; `group by` dice "una fila por
cada medicamento".

> **En el proyecto:** esa es casi exactamente la consulta de `MedicamentoConsultasImpl`. El stock
> total **no se guarda**: se calcula así cada vez, con la fecha de hoy como parámetro (`:hoy`).

### Parámetros (y por qué importan)

Nunca se arma SQL pegando texto que escribió el usuario:

```java
// MAL: inyección SQL. Si q = "x'; drop table usuario; --" se borra la tabla.
"select * from medicamento where nombre like '%" + q + "%'"

// BIEN: parámetro. La base trata q como dato, nunca como código.
"select * from medicamento where nombre like :patron"
```

> **En el proyecto:** todas las consultas usan parámetros. Además, el campo por el que se ordena
> (`sort=nombre`) se valida contra una **lista blanca** (`Ordenamiento.validar`), porque el
> `order by` no se puede parametrizar.

### Índices

Un **índice** es como el índice de un libro: permite encontrar filas rápido sin leer toda la tabla.
Se crean sobre las columnas por las que se busca seguido.

```sql
create index ix_lote_medicamento_vencimiento on lote (medicamento_id, fecha_vencimiento);
-- Índice parcial: solo los lotes con stock (los que interesan para las alertas)
create index ix_lote_vencimiento_con_stock on lote (fecha_vencimiento) where cantidad_actual > 0;
```

## 6. Normalización (1FN, 2FN, 3FN)

Normalizar es **organizar las tablas para no repetir datos**. Los datos repetidos se terminan
contradiciendo: si el nombre de un medicamento está en 50 filas y se corrige en 49, ¿cuál vale?

### Ejemplo de tabla mal hecha

| transferencia | area | area_telefono | medicamento1 | cant1 | medicamento2 | cant2 |
|---|---|---|---|---|---|---|
| 42 | Guardia | 4455 | Paracetamol | 150 | Amoxicilina | 20 |

Problemas: ¿y si son 3 medicamentos? (columnas que se repiten); el teléfono de Guardia se repite
en cada transferencia; si cambia, hay que cambiarlo en todas.

### Primera forma normal (1FN)

**Cada celda tiene un solo valor y no hay columnas repetidas.** Los medicamentos de una
transferencia pasan a ser **filas** de otra tabla (`detalle_transferencia`).

### Segunda forma normal (2FN)

1FN + **cada dato depende de la clave completa**, no de una parte. Solo importa cuando la clave
tiene varias columnas. En el proyecto todas las PK son un solo `id`, así que se cumple sola.

### Tercera forma normal (3FN)

2FN + **ningún dato depende de otro dato que no sea la clave** (sin dependencias transitivas).
Ejemplo: en una tabla `transferencia` con `area_id` y `area_nombre`, el nombre depende de
`area_id`, no de la transferencia. Solución: el nombre vive solo en `area`, y se obtiene con un
`JOIN`.

> **Truco para recordarlo:** cada dato tiene que depender "de la clave, de toda la clave y de nada
> más que la clave".

### Lo que el proyecto NO guarda (para estar en 3FN)

| No se guarda | Porque depende de… | Se obtiene con… |
|---|---|---|
| Nombre del medicamento en el lote | `medicamento_id` | `JOIN` |
| Stock total del medicamento | sus lotes | `SUM` |
| Estado del lote (vencido, por vencer) | la fecha de hoy | se calcula |
| Número `TR-000042` | el `id` | se formatea |
| Total de unidades de la transferencia | sus detalles | `SUM` |

**Única excepción, justificada:** `movimiento_stock.saldo_resultante` guarda el saldo después de
cada movimiento. Es un dato **histórico** ("lo que había en ese momento"), que nunca se modifica,
así que no puede contradecirse. Sirve para auditoría.

## 7. Transacciones (ACID)

Una **transacción** agrupa varias operaciones que tienen que hacerse **todas o ninguna**. Ejemplo:
una transferencia descuenta 3 lotes, crea 3 detalles y 3 movimientos. Si falla en el segundo lote,
¿quedó a medias? No: la transacción se **revierte** (*rollback*) y todo vuelve a como estaba.

| Letra | Propiedad | Qué significa |
|---|---|---|
| **A** | Atomicidad | Todo o nada. |
| **C** | Consistencia | Se pasa de un estado válido a otro válido (se respetan los `CHECK`, FK…). |
| **I** | Aislamiento | Las transacciones simultáneas no se pisan. |
| **D** | Durabilidad | Lo confirmado (*commit*) queda guardado aunque se corte la luz. |

> **En el proyecto:** cada método de servicio con `@Transactional` es una transacción. Si lanza una
> excepción, Spring hace rollback automáticamente. Por eso "todo o nada" en las transferencias sale
> casi gratis: se lanza `StockInsuficienteException` y no queda nada modificado.

## 8. Concurrencia y bloqueos

**Concurrencia** = varias cosas al mismo tiempo. Dos farmacéuticos confirman una transferencia del
mismo medicamento en el mismo segundo:

| Momento | Persona A | Persona B |
|---|---|---|
| 1 | Lee el lote: hay 100. | Lee el lote: hay 100. |
| 2 | Pide 60: 100 ≥ 60, alcanza. | Pide 60: 100 ≥ 60, alcanza. |
| 3 | Guarda 100 − 60 = 40. | Guarda 100 − 60 = 40. |
| Resultado | Se entregaron **120** unidades de un lote de 100 y el sistema dice que quedan 40. ❌ | |

Eso se llama **condición de carrera** (*race condition*).

### Bloqueo pesimista

La solución: **reservar** las filas al leerlas. `SELECT … FOR UPDATE` le dice a la base "estas filas
las voy a modificar; que nadie más las toque hasta que termine".

| Momento | Persona A | Persona B |
|---|---|---|
| 1 | Lee y **bloquea** el lote: hay 100. | Quiere leer y bloquear: **espera**. |
| 2 | Descuenta 60, guarda 40, termina. Se libera el bloqueo. | (esperando) |
| 3 | | Ahora lee: hay **40**. Pide 60: no alcanza → **409 stock insuficiente**. ✅ |

Se llama "pesimista" porque asume que va a haber conflicto y bloquea de entrada. El "optimista"
deja pasar a los dos y falla al guardar si alguien cambió el dato (hay que reintentar).

### Deadlock (abrazo mortal)

| Momento | Transferencia A (pide Amoxicilina y Paracetamol) | Transferencia B (pide Paracetamol y Amoxicilina) |
|---|---|---|
| 1 | Bloquea el lote de Amoxicilina. | Bloquea el lote de Paracetamol. |
| 2 | Quiere el de Paracetamol: espera a B. | Quiere el de Amoxicilina: espera a A. |
| | **Se esperan para siempre.** | |

Solución del proyecto: **bloquear siempre en el mismo orden** (por `id` del lote, `ORDER BY id`).
Si los dos piden primero el lote de menor id, el segundo espera al primero y nunca se cruzan.

## 9. Migraciones con Flyway

El esquema de la base (las tablas) también es código y tiene que versionarse. **Flyway** ejecuta
los archivos `.sql` en orden:

```
backend/src/main/resources/db/migration/
├── V1__esquema.sql                 crea las 8 tablas
├── V2__datos_base.sql              carga las 8 áreas
└── V3__recuperacion_password.sql   agrega la tabla de recuperación
```

Al arrancar, Flyway mira una tabla propia (`flyway_schema_history`), ve cuáles ya aplicó y aplica
las nuevas. **Regla:** una migración aplicada **nunca se edita** (Flyway detecta el cambio y no
arranca). Para cambiar algo, se crea `V4__…`.

Hibernate (la parte de Java que habla con la base) está configurado con `ddl-auto: validate`: solo
**verifica** que las clases coincidan con las tablas; nunca las crea ni las cambia.

## Resumen

| Concepto | En una frase |
|---|---|
| Tabla | Filas (registros) y columnas (campos con tipo). |
| PK / FK | Identificador único / puntero a otra tabla. |
| JOIN | Juntar tablas por sus claves. |
| GROUP BY + SUM | Calcular totales por grupo. |
| CHECK / UNIQUE / NOT NULL | Reglas que la base hace cumplir sí o sí. |
| 3FN | Cada dato depende de la clave, de toda la clave y de nada más que la clave. |
| Transacción | Todo o nada. |
| Bloqueo pesimista | Reservar filas para que nadie las toque mientras las uso. |
| Deadlock | Dos que se esperan mutuamente; se evita bloqueando siempre en el mismo orden. |
| Migración | Archivo `.sql` numerado que cambia el esquema; nunca se edita uno aplicado. |
